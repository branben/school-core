A pipeline that passes every gate — and the agent writes nothing

A dispatch path where admission, worktree creation, agent spawn, and teardown all succeed — but the agent's status writes are silently discarded. The root cause: FM_STATUS_FILE is set in the spawn's process environment (crew_dispatch.py:1007) but is absent from the hand-built prefix that fm-spawn.sh forwards to the crew's pane (fm-spawn.sh:2577). The wrapper sees FM_STATUS_FILE as empty and skips the status-write block. The agent was alive and executing (lastOutputAt set, node_modules/ installed at 07:40 MST) — it just never wrote status verbs that the supervisor could poll. The WATCHER DOWN warning in the spawn stderr is a red herring.

what it sounds like

Dispatch a crew → Orca builds a worktree → FirstMate spawns → agent fixes the issue. Each step has a status check. The pipeline reports success at every gate. The WATCHER DOWN line in the spawn stderr looks like the smoking gun.

what it is

Dispatch a crew → Orca creates a worktree (fine at spawn time) → firstmate sets FM_STATUS_FILE in the spawn's process env (crew_dispatch.py:1007) → fm-spawn.sh forwards a hand-built prefix to the crew's pane (fm-spawn.sh:2577) that omits FM_STATUS_FILE → the wrapper sees FM_STATUS_FILE as empty and skips its status-write block (hermes-fm-wrapper:97) → agent starts, installs deps at 07:40 MST, runs for minutes, writes to stdout (Hermes banner captured in preview) but never writes status verbs → supervisor polls empty status file → timeout → teardown_ok=true → retry sends fail 403 (missing AGENTMAIL_API_KEY). The worktree was NOT broken. The agent WAS alive. The bug is the missing FM_STATUS_FILE in the pane's environment — a 7-line gap in fm-spawn.sh:2577.

root cause 00

The silence is a missing env var in the pane — not a broken worktree, not a dead agent

This is the root cause. The code at crew_dispatch.py:946-954 documents it explicitly:

FM_STATUS_FILE and FM_REPORT_FILE are set in the env= dict at crew_dispatch.py:1007-1008 — this reaches fm-spawn.sh's PROCESS environment. But fm-spawn.sh hands the launch command to the crew's pane as literal typed text (fm-spawn.sh:2638 spawn_send_literal) and forwards only the FM_* vars in its own hand-built prefix at fm-spawn.sh:2577:

FM_ROOT_OVERRIDE= FM_STATE_OVERRIDE= FM_DATA_OVERRIDE= FM_PROJECTS_OVERRIDE= FM_CONFIG_OVERRIDE= FM_PUBLIC_FOLLOWUP_PRIMARY_HOME=... FM_HOME=... FM_TRACE_CONTEXT=... FM_SUPERVISION_MODEL=... $LAUNCH

FM_STATUS_FILE is absent from that list. The string appears nowhere in firstmate's bin/ (it is school-core's own convention). So the wrapper saw FM_STATUS_FILE as empty and skipped its entire status-write block — gated on [[ -n "${FM_STATUS_FILE:-}" ]] (hermes-fm-wrapper:97).

Evidence built into the code: "0 of 366 dispatched crews ever produced the wrapper's failed: hermes-exit--no-terminal-status post-mortem line" — because the wrapper never saw FM_STATUS_FILE, so it never ran its post-mortem check. Meanwhile, 122 of 366 crews DID write status files — by reading the path out of the brief prose instead (brief.md names it; fm-brief.sh:179 templates it in). That's a 122/244 split that tracked whether the model followed a path buried in text, not any transport property. The 244 silent crews — including all 3 of these — relied on the env var that was never in the pane.

what this means The agent WAS alive (lastOutputAt set, node_modules/ installed at 07:40 MST, worktree torn down after agent ran). The agent's output WAS captured (Hermes banner in preview). But the agent's status writes — the done:, working:, failed: lines that the wrapper appends to the status file — were silently discarded because FM_STATUS_FILE was empty in the pane. The agent wrote to stdout (captured in preview), but the wrapper never saw the status file path, so it never wrote the status verbs that the supervisor polls. The supervisor saw nothing, timed out, and marked the crew silent_agent. The bug is NOT in the spawn, the worktree, or the agent. It's in the hand-built prefix at fm-spawn.sh:2577 — missing FM_STATUS_FILE and FM_REPORT_FILE from the vars forwarded to the pane.

convention 05

--setup skip is not the culprit — it skips repo-defined hooks, not the checkout

The spawn recipe passes --setup skip to orca worktree create (backends/orca.sh:134). Per Orca's CLI help, this flag controls the "setup policy for repo-defined setup hooks" — it does not skip the git checkout. Orca always creates a checkout. The reproduction test proves this: the test worktree created with --setup skip has a .git file and full project files. The phantom directory's lack of a .git file (post-teardown) is a different failure — Orca's teardown removed it, not --setup skip.

why it bites You see --setup skip in the spawn recipe and assume it's the cause. Removing it won't fix the silence problem — the reproduction test proves the checkout works fine with --setup skip. The real question is: why did the agent produce no output after starting?

convention 10

AGENTMAIL_API_KEY is missing — a separate bug that collides with the silence

The retry send after cycle 1 and cycle 3 failed with HTTP 403. The cause: AGENTMAIL_API_KEY is not set in the environment. This is a separate bug from the agent silence, but it collides with it — you can't tell from the retry error whether the agent produced nothing (silence) or the send failed (missing key). why it bites The retry mechanism assumes the agent produced something to send. When the send fails with 403, you assume the agent's output couldn't be delivered. In reality, there was no output to deliver, and the 403 is a second, independent failure layered on top. Fixing the key without fixing the silence gives you successful sends of empty reports.

Both cycle meta files store exactly one line for the harness: harness=export. why it bites If the key was missing at spawn time, the agent's first model call would fail silently — no credential, no request, no error visible in the empty terminal tail. convention 12

A crew that writes nothing looks identical to a crew that's still running — until the timeout fires

The crew status file at state/fm-loop-20260920-143509-415.status contains exactly one line — the dispatch-time repo=... marker written by the bridge. The fallback_reason: silent_agent in the crew_run is the timeout's conclusion, not a real-time detection.

why it bites The timeout is the signal that something is wrong, but it doesn't tell you what. Is the agent slow? Is it stuck? Is the worktree empty? Is the output not being captured? why it bites You read tail: [] and conclude "agent never started." But lastOutputAt is set, which proves the agent was alive.
