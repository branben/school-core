Real GitHub issues drive task selection. Verification scores actual output quality. Gates reflect real capability.

Problem: The CURRICULUM dict (autonomous_loop.py:58-197) is 30 static toy problems. Agents have run 50+ rounds producing is_palindrome, factorial, and add(a, b). The EMA score converges to ~70 because every task is trivial and the hardcoded score was 70. The gate system is decorative — no agent ever crosses a gate from real capability growth.

Solution: The issue_bridge already provides real-task drive (GitHub issues). The curriculum should be a fallback, not the primary path. Wire the bridge as the default task source; keep curriculum only for warm-up or when no issues are available. The real fix: agents need to read the codebase before writing code — the issue prompt should include repo context (file paths, existing code), not just the issue title.

  • Agents produce real fixes, not toy functions
  • Verification scores reflect actual output quality
  • Gate crossings become meaningful capability signals
  • Delete 140 lines of static CURRICULUM dict

The verifier should see: repo tree, relevant file paths, the agent's system prompt, and the original issue — then judge whether the response actually addresses the real codebase.

  • Verifier scores substance over structure
  • Hallucinated "Step 1: Identify..." gets low scores
  • Responses referencing real files get high scores

4. Wire triage_classifier into issue_bridge — currently it's a dead-end module

Worth exploring in-process
triage_classifier.py:19-72 — classify_issue()
director.py:139-142 — triage_issue() — never called by issue_bridge
issue_bridge.py:188-210 — bridge_issues() — assumes ready-for-agent

Problem: triage_classifier.py implements a rule-based classifier (label matching, keyword heuristics, body-length analysis) that categorizes issues as bug/enhancement and assigns a workflow state. But issue_bridge.py never calls it — line 188 fetches issues and line 196 iterates them, but the triage step is skipped entirely. The bridge assumes every fetched issue is already ready-for-agent. The classifier only exists as a helper in director.triage_issue() (line 139) which nothing calls.

Solution: Add a triage step in bridge_issues() before dispatch. Call classify_issue(issue["title"], issue["labels"], issue.get("body", "")) and skip issues that return needs-info or needs-triage. This makes the pipeline self-healing — new issues get classified automatically instead of requiring manual labeling.

  • New issues auto-classified on fetch
  • needs-info issues skipped (no wasted agent runs)
  • Classifier's state machine actually exercised

6. Consolidate autonomous_loop.py and issue_bridge.py into one entry point

Speculative ports & adapters
autonomous_loop.py:562 — if __name__ (curriculum + issue mode)
issue_bridge.py:269-280 — bridge_poll() (polling loop)
issue_bridge.py:282-293 — if __name__ (single-run + polling)

Problem: autonomous_loop.py (562 lines) and issue_bridge.py (318 lines) both orchestrate the same pipeline: fetch tasks → dispatch to agents → score results. The autonomous loop has two modes: curriculum (synthetic) and issue-driven (delegates to bridge_issues). The issue bridge has its own polling loop (bridge_poll). Two entry points, two polling implementations, two CLI argument parsers — for what is fundamentally one pipeline.

Solution: Merge into one entry point with mode selection: python -m school --mode issues --repo user/repo (issue-driven, the primary path) or python -m school --mode curriculum (synthetic fallback). One polling loop, one CLI, one place to add features. The issue_bridge flow becomes the default; curriculum becomes a legacy fallback.

  • One entry point, one polling loop
  • Issue-driven mode as default
  • Curriculum mode as fallback (or delete entirely)

Top Recommendation

Candidate 1: Replace the static toy curriculum with a real codebase task adapter.

This is the root cause of the "students produce nothing" problem. The CURRICULUM dict is 30 toy problems that agents have memorized. The EMA converges to 70 because every task is trivial. The gate system is decorative because no task is hard enough to fail.

The issue_bridge already provides the real-task path — it fetches GitHub issues and dispatches them. But the agents don't read the codebase before responding, so they produce generic advice instead of real fixes. The fix is: enrich the issue prompt with repo context (file tree, relevant source files) so agents can produce targeted fixes. Then the verifier (Candidate 3) checks whether the response actually references real files.

Candidates 2 and 5 (delete routing.py, clean dead imports) are quick wins — do them in the same pass. Candidate 4 (wire triage) is needed for the bridge to handle unlabeled issues. Candidate 6 (consolidate entry points) is a follow-up once the pipeline is stable.
